# Sixty-Level Chapter-Gated Progression

## Purpose and Player Outcome

Cutrium will grow from the current twelve-level review build into a sixty-level
Earth-landmark progression without turning the game into a harsh endurance
challenge. The player should encounter a new decision or a fresh arrangement
regularly, complete most levels in roughly 20–45 seconds, and still experience
barrier completion and landmark reveal as the primary reward.

Work is divided into five chapters of twelve levels. Chapter 1 is the existing
implemented set. Chapters 2–5 are implemented one at a time and are separated
by explicit owner playtest gates. Codex must not implement a later chapter
until the project owner gives a direct instruction such as “Chapter 3’e
geçelim.” At every gate, the current build remains playable and testable.

This file is both the requested level implementation roadmap and the living
ExecPlan required by `.agent/PLANS.md`. It must be updated with implementation
progress, playtest findings, tuning changes, validation results, and any scope
decision made during later sessions.

## Current Repository Findings

- The project baseline is Unity `6000.3.21f1` with URP `17.3.0`, Input System
  `1.20.0`, uGUI `2.0.0`, and Unity Test Framework `1.6.0`.
- The only gameplay scene is
  `Assets/Cutrium/Scenes/VerticalSlice.unity`. Gameplay transitions reuse this
  persistent scene.
- The logical board is fixed at 10 by 16 units on every supported device.
  Phone/tablet aspect ratios must not alter gameplay dimensions or difficulty.
- `FirstTwelveGameplayProgression` currently authors exactly twelve levels.
  `CoreFunLevelCatalogDefinition`, `GameplayProgressionSetup`, scene fallback
  behavior, Edit Mode tests, and Play Mode tests contain deliberate assumptions
  that the catalog count is twelve.
- The current twelve-level content already supports configurable threat count,
  spawn position/direction, base speed, Normal/Hunter/Pulse behavior, target
  fraction, barrier speed, minimum cut margin, accepted-cut limit, failed-
  barrier limit, expected completion time, difficulty metadata, Freeze Pulse,
  and Instant Barrier.
- The current threat behavior definition is mutually exclusive: a threat is
  Normal, Hunter, or Pulse. A single Hunter+Pulse threat is not yet supported.
- `PowerConfiguration`, `ThreatMotionSession`, `FirstPlayableController`, and
  `PowerHudPresenter` explicitly model Freeze Pulse and Instant Barrier. Gravity
  Well is approved as the third power but is not implemented.
- `ThreatMotionConfiguration` already carries logical speed and radius. A
  Speedster/Comet is therefore a fast Normal preset, and a Heavy is a slower
  threat with a larger logical radius; neither requires a new solver behavior.
  The current first-twelve factory fixes every radius to `0.35`, so authored
  helpers must expose radius before Heavy content can be created.
- `CaptureLevelConfiguration` already supports both maximum accepted cuts and
  maximum failed barriers. The failed-barrier limit is the gentler pressure
  axis because valid successful cuts do not consume it.
- `CoreFunMetricsTracker` and the Editor-only Level Navigator provide the basis
  for recording completion time, cut use, failures, and power use without
  adding production debug controls.
- `Assets/Cutrium/Content/Earth Landmarks/` contains exactly sixty PNG files.
  During this planning turn the project owner imported them through Unity and
  created all sixty `.meta` files. Read-only validation found sixty non-empty,
  unique 32-character GUIDs. Metadata must never be fabricated, deleted, or
  regenerated by hand. Chapter 1 now authors and validates the first twelve
  imported Sprite references; each later chapter must repeat that validation
  for its newly activated prefix.
- Repository-root `earth-landmarks.md` contains sixty ordered bilingual entries
  matching the alphabetical PNG order. Runtime `LandmarkDefinition` currently
  stores one title/description/sector string and there is no approved
  localization pipeline. The current build already uses Turkish landmark copy,
  so this plan assumes Turkish is serialized for the first playable sixty-level
  catalog and the English copy remains the future localization source.
- Gameplay and landmark catalogs are already architecturally separate and are
  paired by progression index in presentation. This separation must remain.
- The owner supplied separate Normal, Hunter, and Pulse body sprites. Threat
  presentation now resolves these variants and blue/red/green shared-trail
  tints from the existing behavior kind; gameplay motion, speed, radius, and
  collision data remain unchanged.
- Prior automated Unity Test Runner attempts were blocked by the local Unity
  licensing IPC failure. Managed compilation and pure test runners remain
  useful fallbacks, but no Unity suite pass may be claimed without actual test
  results.
- The current worktree also contains owner-created untracked `.claude/` content.
  It is outside this feature and must be preserved. Earth PNGs and
  `earth-landmarks.md` are committed source content.

## Scope

Included:

- Five ordered chapters of twelve levels, ending at exactly Level 60.
- One independently reviewable and shippable catalog prefix after each gate:
  12, 24, 36, 48, then 60 levels.
- Earth landmark definitions paired by index without adding landmark references
  to gameplay types.
- Existing Normal, Hunter, Pulse, target, barrier speed, threat count, spawn
  formation, minimum margin, cut limit, failed-barrier limit, Freeze Pulse, and
  Instant Barrier tuning.
- Behavior-specific Normal, Hunter, and Pulse body sprites and shared-Sprite
  trail tints as replaceable theme presentation, with legacy normal fallbacks.
- Speedster/Comet and Heavy presets using existing speed/radius rules.
- Gravity Well as the approved third power.
- A deterministic timed-level rule and a deterministic escalating-threat rule.
- A readable, deliberately milder Hunter+Pulse composite threat.
- A gated rock/obstacle prototype before committing the final twelve levels to
  obstacle content.
- Chapter-specific setup, validation, Editor navigation, telemetry, intro copy,
  and presentation cues required to make each new rule understandable.
- Edit Mode and Play Mode coverage plus manual checks on a common phone, tall
  phone, and 4:3 tablet.

Explicitly excluded unless later approved:

- Implementing more than one unapproved chapter in a single pass.
- A production localization framework; account systems, economy, monetization,
  online systems, procedural level generation, or third-party dependencies.
- Landscape support or a change to the logical 10-by-16 board dimensions.
- Invisible-but-lethal Casper behavior. A fair Phase/Ghost prototype remains a
  backlog option and is not required for this sixty-level baseline.
- Teleporting threats, deleting threats with a power, auto-capture powers, or
  mechanics that bypass the barrier-and-capture reward.
- Moving or destructible rocks. The obstacle investigation is limited to
  static, axis-aligned logical geometry.
- Hand-editing scene, prefab, or ScriptableObject YAML to materialize catalogs.

## Architecture Proposal

### Chapter-owned authored content

Keep each chapter in a focused authored source rather than growing one
sixty-entry method. A small `MainGameplayProgression` aggregator returns only
accepted and implemented chapters in order. Chapter 1 may continue to use
`FirstTwelveGameplayProgression` initially; later chapter sources return twelve
definitions each. The aggregator validates contiguous display numbers, unique
stable IDs, and a level count divisible by twelve.

The active catalog therefore grows in controlled prefixes:

```text
Chapter 1 accepted        -> Levels  1–12
Chapter 2 accepted        -> Levels  1–24
Chapter 3 accepted        -> Levels  1–36
Chapter 4 accepted        -> Levels  1–48
Chapter 5 accepted        -> Levels  1–60
```

Replace “First 12” setup/count compatibility assumptions with a focused current-
progression path during Chapter 2 implementation. Create and wire a clearly
named main gameplay catalog through Unity Editor APIs. Do not silently overwrite
arbitrary custom/test catalogs, and do not delete the legacy first-twelve asset
until an explicit cleanup is approved.

### Earth landmark content

Create chapter-sized Earth landmark entry groups from `earth-landmarks.md`.
Each entry records a stable ID, Turkish player-facing title, Turkish short
description, location/sector, artwork path, and generated definition path. An
idempotent focused Editor setup imports/configures existing PNGs without
rewriting their bytes and creates only the definitions needed by the currently
implemented catalog prefix.

The `LandmarkCatalog` contains exactly the active gameplay prefix. Runtime
pairing and validation require one valid landmark per playable level and never
read landmark data from a gameplay configuration. Chapter 1 establishes this
policy with twelve entries; each accepted chapter extends the same catalog by
twelve.

### Pressure budget

Every level has one primary pressure and at most one supporting pressure:

- behavior pressure: Hunter, Pulse, or Hunter+Pulse;
- motion pressure: high speed, larger radius, multiple threats, or escalation;
- economy pressure: accepted-cut or failed-barrier limit;
- goal pressure: high target or countdown;
- board pressure: static rock layout.

Target values of 75–86% are normal. Values of 87–90% are reserved for tested
chapter finales or levels with generous barrier/power support. Most levels use
one to three threats. Four threats appear in a few deliberately supported
formation/escalation levels, and five appear once as a slow clustered “swarm”
relief level. Threat count is a tuning axis, not automatic difficulty: higher
counts receive lower speed, target, or rule pressure as needed. A timed rule,
escalation, strict cut limit, and obstacle must never all be stacked. Each
chapter starts easier than the preceding finale and follows a saw-tooth curve
rather than monotonic escalation.

### Gravity Well

Gravity Well is a deterministic spatial-management power rather than another
form of time stop or instant barrier:

1. The player presses the Gravity Well HUD button.
2. A targeting state accepts the next valid board point and does not create a
   barrier from that tap.
3. Invalid/UI/obstacle placement does not consume a charge.
4. For an authored duration, threats in the containing active connected region
   steer toward the fixed point with a bounded deterministic turn. They are not
   teleported and their base speed, logical radius, Pulse phase, and collision
   dimensions are unchanged.
5. Completed barriers and later rock geometry block its influence; it never
   pulls a threat through logical walls.
6. A clear replaceable presentation ring and sand-vortex cue communicate range,
   duration, and activation. Gameplay never reads those assets.

Extend the existing explicit power configuration with Gravity Well charges and
tuning rather than introducing a speculative generic ability framework. If a
fourth production power is later approved, revisit a data-driven list design in
a separate decision.

### Timed challenge

An optional timed configuration belongs to level/session gameplay data. The
countdown begins on the first accepted barrier, not while the intro is visible.
It advances from deterministic simulation time and pauses whenever player input
is authoritatively blocked by a modal transition. Reaching zero enters a clear
retryable `OutOfTime` state. Initial timed levels are generous (40–45 seconds,
78–82% target); only tested late content may approach 35–40 seconds or 85%.

Timed levels receive a compact readable countdown. The last warning interval is
restrained and must not create constant visual stress. Time extensions are not
a third power; Gravity Well remains useful across standard and special modes.

### Escalating-threat challenge

An optional escalation schedule starts from the first accepted barrier and
adds telegraphed threats at authored intervals, normally 10–15 seconds, with a
hard cap of three or four total threats. Five threats are reserved for a static,
slow, pre-authored formation and are not an escalation target in the baseline.
Spawn resolution is deterministic:

- resolve a safe point in an active region using ordered logical candidates;
- keep the full threat circle inside free space;
- stay clear of the active barrier and existing threats;
- telegraph the resolved point before spawning;
- if geometry invalidates a telegraphed point, delay and resolve again instead
  of spawning invisibly elsewhere.

Presentation shows a two-second warning but does not choose the spawn position.
The rule creates natural urgency and therefore is not paired with a strict cut
limit in the baseline progression.

### Hunter+Pulse composite

Avoid a general behavior-composition framework. Add one explicit
`HunterPulse` kind using the already serialized Hunter and Pulse fields, plus
runtime helpers such as `HasHunterReaction` and `HasPulseCycle`. Existing
Normal/Hunter/Pulse data must convert unchanged.

The first composite uses a single threat, a 35–45 degree Hunter turn cap, and
roughly 0.70/1.35 Pulse multipliers. It receives a distinct cue combining the
bounded Hunter reaction and readable Pulse rhythm. No first-introduction level
also uses a timer, cut limit, or obstacle.

### Static rock prototype

The requested behavior—one barrier ending at an internal rock and a later
barrier using another rock edge to isolate a region—cannot be represented by
the current “split one rectangular room into two rectangles” rule. Chapter 5
therefore starts with a one-level technical/gameplay prototype and a separate
owner gate.

The preferred bounded model is static axis-aligned rectangular obstacles plus
an orthogonal free-space cell graph:

- board and obstacle edges partition free space into logical rectangular cells;
- completed barrier segments add blocked connections between cells;
- threat-containing connected components stay active;
- components containing no threat become captured;
- captured percentage sums free-space cell area and excludes solid rock area
  from the denominator;
- threats bounce from logical rock bounds;
- growing barriers raycast to board, completed barrier, or rock boundaries;
- sprites never define collision dimensions.

If this prototype cannot remain deterministic, testable, and readable without
turning into a broad arbitrary-polygon framework, fall back to pre-partitioned
rectangular stone chambers for Chapter 5. The sixty-level catalog must not be
blocked on the full internal-rock design.

### Chapter playtest gate

After each implemented chapter:

1. Codex completes relevant automated validation and reports exact results.
2. The owner plays the new twelve levels through the Level Navigator.
3. The owner records problems and may request focused tuning rounds.
4. The plan records accepted values and validation evidence.
5. Only an explicit owner approval opens the next chapter.

For each level, record at minimum:

| Field | Record |
| --- | --- |
| Completion | success/fail and number of retries |
| Time | first successful completion time |
| Cuts | accepted cuts used / configured limit |
| Breaks | failed barriers / configured limit |
| Capture | largest single capture and final percent |
| Powers | charges used and whether use felt meaningful |
| Readability | whether the intended decision was understood |
| Feel | relaxing / fair / tense / frustrating note |

Normal acceptance aims for 20–45 seconds, clear first-read behavior, no
required blind guess, no repeated full-level failure, and at least one spare
cut in a successful limited-cut run. Tutorial Level 1 may remain shorter.

## Alternatives Considered

- Author all sixty levels in one implementation pass: rejected because balance
  is unvalidated, new mechanics carry different technical risks, and the owner
  explicitly wants chapter-by-chapter playtest control.
- Continue one large `FirstTwelveGameplayProgression` source: rejected because
  its name/count contract is obsolete and a sixty-entry method would be hard to
  review and tune safely.
- Make every new idea a separate threat class: rejected. Speedster and Heavy are
  parameter presets; only Hunter+Pulse requires new behavior logic.
- Use fully invisible lethal Casper: rejected because hidden barrier failure
  conflicts with readable light tension. A translucent, telegraphed Phase
  version may be reconsidered separately.
- Add Barrier Shield as the third power: rejected because Instant Barrier
  already removes barrier exposure. Gravity Well introduces the missing spatial
  decision.
- Make Gravity Well automatically target room center: rejected for the primary
  design because it removes the important “where should I gather?” decision.
- Implement a general power framework now: rejected because only three powers
  are approved and explicit fields minimize migration risk.
- Implement arbitrary polygon drawing to support rocks: rejected. The obstacle
  investigation remains static, axis-aligned, and cell-based with a rectangular-
  chamber fallback.
- Use a sixty-second 89% timer as the first timed level: rejected because normal
  levels target 20–45 seconds and a late failure would feel punitive. It may be
  tested only as a separately approved special challenge.
- Pair landmarks directly inside gameplay definitions: rejected because it
  violates the established gameplay/presentation separation.

## Risks and Unknowns

- All proposed values after Level 12 are balance hypotheses. The existing
  twelve also remain pending owner metrics; no numeric value is “fun” merely
  because a structural test accepts it.
- Generalizing twelve-specific compatibility code can accidentally replace
  custom/test catalogs. Migration recognition must remain exact and covered.
- The Earth PNGs now have owner-created Unity `.meta` files with unique GUIDs.
  Deleting or regenerating that metadata would break future catalog references;
  import settings and Sprite subassets must be checked without rewriting the
  artwork bytes.
- Runtime copy is presently single-language. Turkish is an assumption for the
  current build; adding an English toggle is a separate localization decision.
- Gravity targeting adds a temporary input mode. It must clearly suppress a
  barrier gesture for the placement tap and exit cleanly on cancel, retry,
  completion, and scene disable.
- Dynamic threat spawning after room subdivision is a deterministic geometry
  problem, not a presentation choice. Warning points can become invalid and
  require a fair delay/re-resolution policy.
- A hard timer can become punishing if capture presentation or blocked input
  consumes time. Timing ownership must be explicit and tested.
- Composite behavior may be difficult to read if visual cues overlap. If human
  reviewers cannot identify its phases reliably, reduce its values or remove it
  instead of increasing tutorial text.
- Internal rocks are the largest architectural risk because they replace the
  rectangular-room split assumption. The Level 49 gate and chamber fallback are
  mandatory containment measures.
- More simultaneous threats, cell graphs, and presentation trails can increase
  mobile CPU/overdraw. Four is the normal special-case cap; the single five-
  threat Level 54 uses slow Normal threats on an open board and remains
  provisional until solver, presentation-pool, and mobile profiling evidence is
  recorded.
- Unity licensing may continue to block command-line Test Runner/setup work.
  Licensed interactive Editor validation and explicit manual handoff remain
  required when that occurs.
